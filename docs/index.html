libSQL / sqld · self-hosted · one operator per box

A private SQLite platform on your own box.

sqlitend runs sqld (libSQL's embeddable server) as plain subprocesses on the machine you already have — no containers, no cluster, no vendor. Create a database, get a connection URL and a token, and point any libSQL client at it. The whole round trip takes under a minute.

What it is

SQLite scale-out isn't the point.
Being able to self-host it is.

SQLite is the most deployed database in the world, and sqld turns each one into a real network server: Hrana — libSQL's WebSocket wire protocol — over ws://, HTTP, live replicas. The piece everyone was missing is the boring operator — something to create, run, secure, monitor, and retire databases without standing up yet-another-control-plane. sqlitend is that operator: one per machine, REST on the front, plain directories on disk.

Point a libSQL client at a URL and a database answers — exactly like a hosted service, except the data never leaves your box and nothing in the stack is bigger than one binary and one Bun process.

Every database gets its own sqld process on the pinned, SHA-256-verified binary. The control plane supervises it: launch, ready-probe, crash detection, restart adoption, clean delete. A database is a first-class object with an id, a data directory, a per-DB http+grpc port pair (6101–6300), and metrics — not a container you have to feed.

Before this page existed, sqlitend was load-tested and reviewer-gated. The numbers are below, with the raw evidence JSON linked on each card.

Isolation by key, not by folder

Each database owns an Ed25519 signing keypair. Tokens are signed per-database — a token for users is rejected by orders. Cross-DB access is cryptographically impossible, not just policy.

Full-access tokens with a lifespan

Issue full-scope tokens that expire (24h default). No shared platform password. sqld validates JWTs statelessly, so revoke-by-jti is not supported in v1 — to drop a leaked token, use a short TTL or delete and re-create the database (it re-keys).

Subprocesses, not containers

No Docker daemon, no orchestration. The pinned binary runs supervised under the control plane — crash recovery and restart adoption included. The whole platform is a couple of processes.

Live per-database metrics

Per-DB CPU and RSS sampled straight from /proc, served to the dashboard and to /api/databases/:id/metrics. See a hot database before your users do.

The single-writer wall

sqld is single-writer. Aggregate write throughput is flat at ~2,250/s from 1 to 4 clients on one core, declines past 8, and thrashes beyond 16 — that is sqld's design, not a bug in sqlitend. The lever is batching: single-row insert overhead drops from ~20× to 3.4× at 1,000 rows per statement (point lookups stay ~100× — per-statement by nature).

One finding worth knowing before write-heavy HA: a sustained write-heavy run left the benchmark sqld process busy-spinning at 100% CPU with zero clients attached (host load ~56 on one core). It killed cleanly, and the read-heavy million never showed it — but batch writes, pool connections, and watch per-DB sqld CPU. The read side is a different story: 80/20 at a million statements, zero errors.

And in v1 the control plane itself has no login — on a public bind, put it behind a firewall or an authenticated reverse proxy.

Run it

One command. Under a minute. No root.

The installer handles everything: Bun if missing, the repo, the pinned sqld binary (SHA-256 verified), the web build, and a sqlitend launcher in ~/.local/bin. All data and keys live under ~/.local/share/sqlitend. Upgrading later: re-run the same installer against a newer SQLITEND_BRANCH; when the pinned sqld version moves, the new checksum ships in fetch-sqld.sh (upgrade SOP ↗).

install curl -fsSL https://raw.githubusercontent.com/thaqiif/sqlitend/main/scripts/install.sh | bash

Before you pipe it: read install.sh and the per-OS sqld checksums pinned in fetch-sqld.sh — the installer verifies them on every run.

01

Install

One line, about a minute. Options: SQLITEND_BRANCH, SQLITEND_INSTALL_DIR, SQLITEND_SYSTEMD=1 for a systemd user service.

# terminal
curl -fsSL …/scripts/install.sh | bash
02

Start

Control plane binds 0.0.0.0:6100 by default — reach it from any interface on the LAN/VPN. SQLITEND_HOST=127.0.0.1 goes local-only.

# terminal
~/.local/bin/sqlitend
03

Create + token

Workspace → database → token via REST (or the dashboard at :6100). The API table below is the whole surface.

POST /api/workspaces          {"name":"labs"}
POST /api/workspaces/:id/databases {"name":"users"}
POST /api/databases/:id/tokens {"expiresInHours":24}
04

Connect

Any libSQL client. Set SQLITEND_PUBLIC_HOST so advertised URLs point at your machine, not loopback.

// any libSQL client
const c = createClient({
  url: "libsql://<host>:6121",
  authToken: token,
});
await c.execute("select * from users");

Explore the API

The whole control plane is one REST surface.

JSON in, JSON out. Every mutating call is validated with zod — strict 400s, no silent defaults. This table is the complete route surface.

MethodPathWhat it does
GET/api/systemVersion, sqld status, publicHost, workspace & database counts
GET/api/workspacesList workspaces
POST/api/workspacesCreate a workspace — {"name"}
DELETE/api/workspaces/:idDelete a workspace — must be empty (409 otherwise); delete its databases first
GET/api/databases · /api/databases/:idList / inspect databases — status, port pair (connection URLs via /connection)
POST/api/workspaces/:id/databasesCreate a database — spawns its supervised sqld
POST/api/databases/:id/start · /stopStart / stop the sqld process
DELETE/api/databases/:idKill + remove the database and its data directory
GET/api/databases/:id/connectionLive connection URL + current token for any client
GET/api/databases/:id/tokensList issued tokens
POST/api/databases/:id/tokensMint a full-access token — {"expiresInHours"}
DELETE/api/databases/:id/tokens/:jtiRevoke by jti — 501 in v1 (stateless JWT); use short TTLs or re-create the DB
GET/api/databases/:id/metricsSampled CPU / RSS / disk / uptime (5s default)

Web dashboard: same data at :6100, served by the same backend through the API proxy.
