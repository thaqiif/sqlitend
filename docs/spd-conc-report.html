The Million-Statement Run

One million statements, four concurrent clients, one isolated sqld database on a single-core virtual machine — and not one failure. This is what happens when you stop asking SQLite “how fast?” and start asking a server “how busy can you get?”

1The concurrency curvewrite-heavy 30/70 mix · 35 s per level

Before the million, a sweep: 1, 4, 8, then 16 simultaneous clients, each running an identical mixed workload against the same seeded database. The headline is a wall, not a curve — sqld has a single writer thread, so aggregate throughput is flat at roughly 2,200 statements per second from one client to four. Concurrency buys queueing, not speed: p95 latency quadruples by 16 clients and the box stops cooperating entirely past that point (the run at 32 and 64 clients collapsed; the 1-minute load average hit 56 on one core). Zero errors at every level — the server said no politely, by returning SQLITE_BUSY, and the client retried with backoff exactly as a production driver would.

2The million-statement runread-heavy 80/20 mix · fresh DB · 4 clients · 666.8 s

A brand-new database, seeded with 100,000 rows, then four clients hammering it with a realistic serverless OLTP mix — 12% single-row inserts, 8% point updates, 35% indexed point reads, 25% range counts, 20% top-N reads — until exactly 1,000,000 statements had been served. The wall from the sweep was the write-heavy part; at this mix the same wall stands far away. Throughput held a mean of 1,500 /s for eleven minutes, and the tail was astonishingly calm.

3The wall is real — and it isn’t the network

Single-writer, by design

sqld serializes writes through one writer thread — exactly as SQLite itself does, only across a socket. The sweep’s flat ceiling (~2,200/s at 1–4 clients) is that serialization on one core. The practical law it implies: per-statement round trips are the currency, so batch your writes. In the companion speedtest replication, 1,000-row batches cut serverless overhead from 20× to 3.4×.

One real bug found

A sustained write-heavy run (30% writes, retry storms, growing table) left the benchmark sqld process busy-spinning at 100% CPU with zero clients attached — load 56 on one core, machine otherwise idle. Killing the process ended it instantly; the read-heavy million ran eleven minutes without a trace of it. This is a sqld behavior worth knowing before you run heavy write concurrency against a solo node: monitor per-database CPU and batch aggressively.

MMethod & honesty

How it ran

The sweep and the million used one sqlitend-created database each, one minted full-access token, @libsql/client 0.18.0 over Hrana WebSocket to ws://127.0.0.1 — loopback, so no real network in the numbers. Both databases were seeded with 100,000 rows. The sweep mix was write-heavy (30%); the million mix read-heavy (20% writes) and is labeled as such — rates across the two are not directly comparable. Latency was bucketed at 50µs resolution; client-visible latency includes retry backoff. Each run was a fixed-quota batch, so the million is exactly 1,000,000 statements — every one counted.

Caveats

One core, one gigabyte, loopback — absolute rates are box-relative; the shape (flat writer ceiling, calm read tail) is the portable lesson. The write-heavy sweep thrashes at ≥32 clients and is reported as such, not hidden. The sqld busy-spin was observed once and mitigated; it deserves a dedicated investigation before claiming write-heavy HA. A real network, TLS, and more cores would all move these numbers and are the obvious follow-up. The control plane has no login in v1: firewall or reverse-proxy it in production.
